# CampusFlow
#### Video Demo: https://youtu.be/oWJdq0RlFXM
#### Description:

CampusFlow is a college event management system for managing students, events, registrations, teams, payments, and feedback. Campus events can leave participant lists, team details, payment records, club information, and feedback scattered across different systems. CampusFlow brings these related records together in a MySQL relational database and provides a dashboard for managing the complete event workflow.

The intended users are student organizers, club coordinators, and faculty advisors. CampusFlow is designed as a management portal rather than a public event-discovery site. From the dashboard, users can view summary information, manage student and event records, create teams, register individual students or teams, track payments, update registration status, and collect feedback from eligible participants.

The backend is written in Python using Flask. `backend/app.py` creates the Flask application, registers the resource blueprints, exposes `/api/health`, adds CORS headers, and defines JSON error handlers. The API is divided into focused route files: `student_routes.py`, `event_routes.py`, `team_routes.py`, `registration_routes.py`, `payment_routes.py`, and `feedback_routes.py`. `backend/db.py` centralizes MySQL access using PyMySQL. It creates connections using settings from `backend/config.py`, returns query results as dictionaries, commits writes when requested, handles database errors, and closes connections after use.

The frontend is a static single-page dashboard built from `frontend/index.html`, `frontend/styles.css`, and `frontend/script.js`. The HTML defines the sidebar, dashboard sections, shared modal, and toast containers. JavaScript uses the `fetch` API to communicate with the Flask backend at `http://127.0.0.1:5001`, renders API data into tables and dashboard panels, generates modal forms, refreshes data after operations, displays notifications, and provides client-side search and filtering. The CSS defines the visual layout, including the fixed sidebar, responsive mobile menu, statistic cards, scrollable tables, status badges, forms, modals, and toast messages. The top-level `package.json` and `index.js` are minimal Node scaffolding and are not the main application runtime.

The database is defined in `databases/schema.sql`. `STUDENT` stores student identity and academic information, with unique roll number and email values. `CLUB` and `VENUE` store organizer and location data, while `EVENT` references them and stores its title, type, schedule, registration type, capacity, and fee. `TEAM` belongs to an event and references a student leader, while `TEAM_MEMBER` represents the relationship between teams and students. `REGISTRATION` connects students to events and can optionally reference a team. It has a unique `(STUDENT_ID, EVENT_ID)` constraint to prevent duplicate registrations. `PAYMENT` references registrations, and `FEEDBACK` references registrations, students, and events. The schema also contains `CLUB_MEMBERSHIP`, `ORGANIZER_ROLE`, `SPONSOR`, and `SPONSORSHIP`; however, the current frontend and API concentrate on the core event-management workflow.

Registration is one of the central workflows. `POST /api/registrations` verifies the student and event, checks capacity when `MAX_CAPACITY` is defined, validates an optional team against the same event, and prevents duplicate student-event registrations. `POST /api/registrations/team` obtains members from `TEAM_MEMBER`, falls back to the leader when necessary, checks for duplicate members and available capacity, and creates one registration record for each team member.

Payment behavior depends on the event fee. For an event where `FEE > 0`, a new registration starts with status `PENDING`, and the backend automatically creates a `PAYMENT` row with mode `ONLINE`, status `PENDING`, and the event fee as its amount. Free-event registrations start as `REGISTERED` and do not create payment records. The payment API supports `CASH`, `UPI`, `CARD`, `BANK_TRANSFER`, and `ONLINE`, with `PENDING` and `SUCCESS` statuses. Creating, updating, or patching a payment to `SUCCESS` automatically changes a pending registration to `REGISTERED`.

Registration status is managed through `PATCH /api/registrations/<registration_id>`. Valid statuses are `PENDING`, `REGISTERED`, `CONFIRMED`, and `ATTENDED`. Paid registrations cannot leave `PENDING` until payment is successful, and a successful payment prevents a registration from being returned to `PENDING`. Free events cannot use `PENDING`. These business rules are enforced in the Flask routes rather than through SQL enum or CHECK constraints.

Feedback is handled through the feedback API. It must reference a matching registration, student, and event, and ratings must be integers from 1 to 5. Comments are optional, while duplicate student-event feedback is blocked. Feedback is available only for registrations with status `CONFIRMED` or `ATTENDED`. Filtering feedback by `event_id` also provides the average rating and response count.

The main design decision is a clear separation of responsibilities. Flask blueprints keep backend resources focused and maintainable, the frontend handles interaction and presentation, and MySQL maintains the relationships between the application's entities. Important business rules, particularly payment-dependent registration status, are enforced on the backend instead of relying only on client-side checks. Validation includes required-field checks, foreign-key verification, rejection of negative values, validation of allowed statuses and payment modes, duplicate prevention, and database integrity-error handling. PyMySQL parameter binding is used for user-supplied SQL values. The frontend adds usability checks such as valid event time ordering, non-negative numeric inputs, and 10-digit phone validation.

CampusFlow does not currently implement login, password handling, sessions, or role-based authorization. It should therefore be considered an administrative project prototype rather than a production-secured system. A typical workflow begins when the dashboard loads data from the API. An organizer can add students and events, create a team by selecting members and a leader, and register an individual or entire team. The backend creates the required registration and, for paid events, payment records. Once payment succeeds, the registration can progress through its allowed statuses, and confirmed or attended participants can submit feedback. This keeps event participation, payment state, and post-event feedback connected in one system.
